# 基于 MongoDB 的问卷系统第一阶段实验报告

## 0. Github 仓库地址:https://github.com/luyian2006/Questionnaire-System.git

## 1. 项目目标与功能范围

### 1.1 项目目标

本项目实现一个简化版在线问卷系统，功能定位接近问卷星或 Google Forms。系统允许注册用户创建问卷、配置题目和条件跳转规则，通过分享标识发布问卷，要求填写者登录后完成答题，并将最终答卷持久化到 MongoDB。问卷所有者可以查看自己问卷的统计结果。

### 1.2 第一阶段范围

已实现的核心范围如下：

- 用户注册、登录、PBKDF2 密码哈希和 Bearer Token 身份认证。
- 用户只能查看和管理自己创建的问卷。
- 问卷草稿、发布、关闭、截止时间和唯一分享标识。
- 单选题、多选题、文本填空题、数字填空题。
- 单选、多选和数字题的条件跳转规则。
- 发布前的问卷定义校验，包括题目、选项、规则、目标和保守循环检查。
- 服务端重新计算答题路径，校验必答题、答案格式、路径外答案和未知题目答案。
- MongoDB 中的用户、问卷版本和最终答卷持久化。
- 单选、多选、文本、数字题统计，以及整体统计和按题目统计。
- 默认禁止同一账号重复提交；问卷设置 `allow_multiple_submissions=true` 后允许重复提交。

本阶段不追求生产级前端和复杂会话管理。项目后续增加了一个由 FastAPI 直接提供的轻量演示页面，可完成注册登录、示例问卷管理、分享答题和统计查看；已记录的真实业务验收仍以 Swagger UI 为主。`start_question_id` 尚未实现；提交路径默认从按 `order` 排序后的第一题开始。没有进行中的答卷保存、所有者原始答卷明细/导出接口，也没有单独的跨版本合并统计策略。

## 2. 系统架构与业务流程

### 2.1 分层结构

系统由以下部分组成：

1. `app/main.py` 创建 FastAPI 应用、注册生命周期和健康检查。
2. `app/api.py` 提供认证、问卷管理、分享查询、导航、提交和统计接口。
3. `app/services.py` 负责用户、问卷版本、发布/关闭、答卷保存和统计等业务编排。
4. `app/algorithms/answer_validator.py` 负责单题答案校验。
5. `app/algorithms/survey_validator.py` 负责发布前问卷定义校验。
6. `app/algorithms/jump.py` 负责纯 Python 跳转导航和提交路径验证，不访问 HTTP 或数据库。
7. `app/db/mongo.py` 创建 MongoDB 客户端、数据库连接和索引。
8. `app/dependencies.py` 解析 Bearer Token 并取得当前用户。

### 2.2 主要业务流程

注册和登录流程为：用户注册 -> 用户名规范化和唯一性检查 -> PBKDF2 哈希密码入库 -> 登录校验密码 -> 签发 Bearer Token -> 受保护接口根据 Token 获取用户。

问卷管理流程为：所有者创建草稿 -> 配置元数据和题目 -> 编辑草稿；如果当前版本已发布，编辑会复制出新的草稿版本 -> 发布时调用问卷定义校验器 -> 校验通过后将该版本标记为不可直接覆盖的已发布版本 -> 生成/使用唯一 `share_slug` -> 所有者可以关闭问卷。

填写流程为：填写者通过 `GET /surveys/share/{share_slug}` 读取已发布且开放的问卷定义 -> 登录后调用导航接口 -> 服务端调用 `resolve_next_step()` 计算下一题 -> 最终提交时调用 `validate_submission()`，重新从第一题遍历实际路径 -> 只校验实际路径上的题目和答案 -> 检查重复提交策略 -> 将答卷及版本快照写入 `responses`。

匿名边界采用“登录后匿名”语义：填写者仍必须登录，系统内部保存 `respondent_user_id` 用于认证和重复提交控制，但所有者统计接口不返回填写者身份。分享问卷定义的 GET 接口可以公开读取；导航和最终提交必须登录。关闭或超过截止时间后，分享查询、导航和提交均拒绝访问。

## 3. MongoDB 集合设计、索引设计与选型理由

### 3.1 集合设计

项目使用三个核心集合：`users`、`surveys` 和 `responses`。完整字段和示例见 [database-design.md](database-design.md)。

`users` 保存认证身份，包括用户名、规范化用户名、密码哈希、密码算法、创建时间、更新时间、最近登录时间和状态。系统不保存明文密码。

`surveys` 保存所有者、标题、描述、分享标识、匿名和重复提交配置、截止时间、问卷状态、当前版本、已发布版本以及嵌入式版本数组。每个版本内嵌题目、选项、答案约束和跳转规则。嵌入问卷定义便于一次加载完整配置，也保留版本历史。

`responses` 独立保存最终答卷，包括问卷 ID、所有者 ID、问卷版本、提交者内部 ID、匿名标记、答题、服务端计算路径、问卷快照、开始/提交时间和提交状态。答卷不嵌入 `surveys`，避免问卷文档无限增长和高并发写冲突。

### 3.2 索引设计

应用启动时由 `app/db/mongo.py` 建立以下索引：

| 集合 | 索引 | 作用 |
| --- | --- | --- |
| `users` | `username_normalized` 唯一 | 防止重复用户名，支持登录查找 |
| `users` | `created_at` 降序 | 支持用户时间排序查询 |
| `surveys` | `share_slug` 唯一 | 保证分享链接标识唯一 |
| `surveys` | `owner_user_id, updated_at` | 查询所有者自己的问卷列表 |
| `responses` | `survey_id, submitted_at` | 按问卷查询答卷并按提交时间排序 |
| `responses` | `survey_id, survey_version` | 按问卷版本筛选统计 |
| `responses` | `respondent_user_id, survey_id` | 支持填写者和问卷关联查询 |
| `responses` | `survey_id, submission_key` 唯一部分索引 | 默认策略下防止同一账号重复提交 |
| `responses` | `survey_id, answers.question_id` | 支持按题目查询答卷 |

MongoDB 适合本项目的原因是：问卷题目、选项、不同题型约束和跳转规则具有嵌套且异构的结构，使用文档和嵌入版本可以在读取问卷时一次取得完整定义；答卷是不断增长且独立写入的记录，单独集合便于并发写入和统计查询；版本快照保留了历史答卷的解释依据。课程明确要求使用 MongoDB 且不允许关系数据库，本设计没有引入关系数据库，也没有使用现成问卷系统框架。

## 4. 核心算法

### 4.1 答案校验

`app/algorithms/answer_validator.py` 的 `validate_answer()` 区分答案缺失、显式 `None` 和已提交但无效的答案对象。答案对象必须包含与题目一致的 `question_id`、`type` 和 `value`。

- 单选题要求标量 `option_id` 存在于题目选项。
- 多选题要求列表、选项全部合法且不重复，并检查 `min_selected`、`max_selected` 和优先级更高的 `exact_selected`。
- 文本题要求字符串，检查必答空字符串以及最小/最大长度。
- 数字题拒绝布尔值、`NaN`、正负无穷和非数值；检查有限性、整数限制、最小值和最大值，并能处理超大整数而不泄漏 `OverflowError`。

错误使用结构化错误码，例如 `missing_required_answer`、`invalid_answer_type`、`invalid_answer`、`invalid_answer_option`、`duplicate_answer_option` 和 `number_not_finite`。

### 4.2 问卷定义校验

`app/algorithms/survey_validator.py` 的 `validate_survey_definition()` 在发布前检查：非空题目列表、题目 ID 唯一、`order` 有效且唯一、题型和必填字段、选项 ID 唯一、题型约束、规则优先级唯一、条件操作符和条件值、跳转目标存在或为合法 `end`。规则按题目类型限制：单选支持 `equals`、`not_equals`、`in`；多选支持集合和选择数量操作符；数字题支持比较和 `between`。最后将默认顺序和跳转目标构成图，按第一阶段保守规则拒绝可能循环，返回 `jump_cycle_detected`。

### 4.3 跳转逻辑

`app/algorithms/jump.py` 的 `resolve_next_step(questions, question_id, answers)` 先校验并按 `order` 排序题目，再定位当前题。当前题不存在、空题目列表、重复题目 ID、重复 `order`、非法选项定义、`jump_rules=None` 等损坏定义会返回稳定的结构化错误。没有答案时返回 `awaiting_answer`，不执行规则；有答案时先校验答案，再按 `priority` 升序检查规则，只执行第一条匹配规则。没有匹配规则时进入默认下一题，最后一道题返回 `end`。跳转目标可以是题目或 `end`。

`condition_matches()` 支持单选、 多选和数字题条件。缺失答案不会匹配 `not_equals`，多选缺失值不会触发 `TypeError`，文本题不是第一阶段的跳转条件来源。发布校验拒绝相同题目的重复优先级，因此运行时不依赖 `rule_id` 解决同优先级冲突。

### 4.4 提交路径校验

`validate_submission(questions, answers, max_jump_steps=None)` 由服务端从排序后的第一题开始，反复调用导航逻辑并记录路径。它只要求实际路径上的必答题有合法答案，允许跳过合法跳转中的必答题；可选题缺失时不执行该题规则并按默认顺序前进。未知题目答案和路径外答案被拒绝，已提交但格式错误的答案不会被误报为缺失答案。

函数返回 `valid`、`path`、`errors`，成功时还返回 `skipped_required_questions`。运行时重复访问题目返回 `jump_cycle_detected`，超出显式 `max_jump_steps` 返回 `max_jump_steps_exceeded`，非法运行时目标返回 `invalid_runtime_target`。这层防御不能替代发布时循环校验。

## 6. 问题、解决方法与已知限制

### 6.1 已解决问题

1. 数字答案校验曾可能在超大整数比较或转换时出现未处理异常。现通过有限数值判断和回归测试处理 `10 ** 10000`、`NaN`、正负无穷。
2. 题目输入可能乱序。跳转和提交路径现在都按 `order` 排序，并拒绝缺失、重复或无效顺序。
3. 空选项、未知选项、重复选项和多选重复选择可能绕过校验。现在由答案校验和发布校验共同拒绝。
4. 缺失答案和无效答案需要区分。当前使用 `MISSING`、显式 `None` 和结构化错误码区分。
5. 客户端可能伪造路径或提交被跳过题目。最终提交由服务端重新计算路径并拒绝路径外答案。
6. 发布时的未知跳转目标、重复优先级和循环配置会被拒绝；运行时仍保留循环和最大步数防御。
7. 发布后修改会创建新的草稿版本，旧版本和历史答卷不直接覆盖。

## 8. 项目总结

第一阶段完成了一个可启动、可通过 HTTP API 演示、使用 MongoDB 持久化的问卷系统最小闭环。系统将问卷定义、版本、答案校验、发布校验、跳转和提交路径验证分层实现，避免将跳转规则写死在路由中；使用独立 `responses` 集合保存答卷，并通过索引支持用户名、分享链接、问卷查询和重复提交控制。自动化回归和真实隔离数据库验收共同证明主要课程功能可运行。

第一阶段的主要后续工作不是重写核心算法，而是根据第二阶段需求补齐 `start_question_id` 语义、进行中答卷、答卷明细/导出、跨版本统计策略和前端体验，并在新增需求下继续保持已发布版本和历史答卷的可解释性。
