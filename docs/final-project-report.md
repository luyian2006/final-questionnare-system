# 基于 MongoDB 的在线问卷系统最终实验报告

## 1. 项目概述

### 1.1 项目目标

本项目按照课程大作业要求，实现一个简化版在线问卷系统。系统使用 FastAPI、PyMongo 和 MongoDB 作为后端与数据存储，使用原生 HTML、CSS 和 JavaScript 提供轻量前端，不使用关系数据库或现成问卷系统框架。

项目采用两阶段迭代方式完成。第一阶段实现账号、问卷、四种题型、条件跳转、答卷提交和统计等基础业务闭环；第二阶段在保留第一阶段结构和数据兼容性的前提下，引入题目身份、不可变题目版本、共享与派生、问卷题目快照、题目使用情况和同版本跨问卷统计。

### 1.2 技术栈

| 层次 | 技术 |
| --- | --- |
| 后端框架 | FastAPI |
| 数据访问 | PyMongo |
| 数据库 | MongoDB |
| 前端 | 原生 HTML、CSS、JavaScript |
| 测试 | pytest、FastAPI TestClient、内存数据库替身 |
| 认证 | Bearer Token、PBKDF2 密码哈希 |

### 1.3 最终功能范围

- 用户注册、登录、密码哈希和登录状态恢复。
- 用户只能管理自己的问卷；填写导航和提交需要登录。
- 问卷创建、编辑、发布、关闭、截止时间、分享链接和重复提交策略。
- 单选、多选、文本和数字四种题型及其校验规则。
- 单选、多选和数字题条件跳转；发布前定义校验；提交时服务端重新计算实际路径。
- 已发布问卷版本不可直接覆盖，后续编辑创建新草稿版本。
- 最终答卷保存问卷版本、题目快照、答案和服务端计算路径。
- 问卷级四种题型统计。
- 题目库、题目不可变版本、历史版本查看和恢复。
- 题目共享、取消共享、他人派生为独立题目。
- 选择指定题目版本加入问卷，并保存来源题目和来源版本标识。
- 查询题目在哪些问卷版本中被使用。
- 按精确题目版本进行脱敏跨问卷统计。
- FastAPI 直接提供的轻量浏览器前端和 Swagger API 页面。

## 2. 课程要求与两阶段需求变化

### 2.1 课程总体要求

课程要求使用 MongoDB 保存业务数据，不能改用关系数据库；必须说明数据库设计、业务逻辑、关键算法、测试过程和 AI 使用过程。项目需要先完成初始需求，再根据第二阶段新增需求修改原系统，不能另起一个全新系统，也不能删除第一阶段核心功能。

提交材料至少包括源码、MongoDB Schema 或数据库设计、系统说明、API 说明、关键逻辑说明、测试步骤与结果、项目完成报告和 AI 使用记录。

### 2.2 第一阶段需求

第一阶段以完整问卷闭环为目标：用户注册登录、创建和管理自己的问卷、配置四种题型和跳转规则、通过分享链接填写、保存答卷并查看统计。填写者需要登录；匿名配置表示对问卷所有者隐藏身份，系统内部仍保留填写者 ID，用于认证和重复提交控制。

第一阶段采用 `users`、`surveys` 和 `responses` 三个核心集合。题目直接嵌入问卷版本，答卷独立保存，并记录问卷版本和题目快照，从而保证历史答卷可以被正确解释。

### 2.3 第二阶段需求变化

第二阶段要求题目可以跨问卷复用，并且需要处理共享、版本、权限和历史数据一致性。主要变化如下：

| 第一阶段 | 第二阶段变化 |
| --- | --- |
| 题目只存在于问卷版本中 | 新增独立题目身份和不可变版本 |
| 题目只能随问卷编辑 | 题目可创建新版本、查看历史和恢复旧版本 |
| 没有题目共享 | 登录用户可使用共享题目，但不能修改原作者题目 |
| 问卷题目没有题库来源 | 从题库复制时记录来源题目 ID 和来源版本 ID |
| 统计以单份问卷为范围 | 增加同一个题目版本的跨问卷脱敏统计 |
| 前端以基础问卷流程为主 | 增加题目库、版本、共享、派生、复用和跨问卷统计入口 |

第二阶段没有改变第一阶段题目的实际结构。题目版本中的 `content` 继续使用 `type`、`title`、`description`、`required`、`options`、`validation` 和 `jump_rules` 等字段，因此原有答案校验、问卷校验、跳转和提交算法可以继续复用。

## 3. 系统架构与项目结构

### 3.1 分层结构

系统按职责分为以下部分：

1. `app/main.py`：创建 FastAPI 应用、生命周期、路由、静态前端和健康检查。
2. `app/api.py`：认证、问卷、分享答题、提交和问卷统计接口。
3. `app/question_api.py`：第二阶段题目库、题目版本、派生、使用情况和跨问卷统计接口。
4. `app/services.py`：第一阶段用户、问卷、版本、答卷和统计业务逻辑，以及问卷题目来源字段的可信写入边界。
5. `app/question_services.py`：题目身份、不可变版本、共享权限、派生、题目快照复用和跨问卷统计。
6. `app/algorithms/`：与 HTTP 和数据库无关的答案校验、问卷定义校验、跳转和提交路径算法。
7. `app/db/mongo.py`：MongoDB 客户端、数据库访问、健康检查和索引初始化。
8. `app/dependencies.py`：Bearer Token 解析和当前用户依赖。
9. `frontend/`：FastAPI 同源提供的 HTML、CSS 和 JavaScript 页面。
10. `tests/`：纯算法、API 业务、健康检查和第二阶段回归测试。

### 3.2 主要业务流程

问卷业务流程为：注册和登录 -> 创建问卷草稿 -> 配置或复用题目 -> 发布前校验 -> 生成可填写链接 -> 登录填写者按规则答题 -> 服务端重新计算路径 -> 保存答卷和问卷快照 -> 所有者查看统计。

题目库业务流程为：创建题目并生成 v1 -> 创建不可变新版本或从历史版本恢复为新版本 -> 选择是否共享 -> 其他登录用户查看、复用或派生 -> 指定版本完整复制到问卷草稿 -> 问卷发布和填写 -> 题目所有者按来源版本查看使用情况和跨问卷聚合统计。

## 4. MongoDB 数据库设计

### 4.1 集合划分

最终系统使用五个集合：

| 集合 | 主要职责 |
| --- | --- |
| `users` | 用户名、密码哈希、注册时间和账号状态 |
| `surveys` | 问卷所有者、元数据、生命周期和嵌入式问卷版本 |
| `responses` | 最终答卷、问卷版本、题目快照、路径和内部填写者标识 |
| `question_items` | 题目身份、所有者、共享状态、当前版本和派生来源 |
| `question_versions` | 不可变题目内容、版本号、创建者和版本来源关系 |

没有把所有数据放入一个集合，也没有把题目、选项和规则过度拆分。问卷需要一次读取完整定义，因此问卷版本继续嵌入题目；答卷持续增长且需要独立写入，因此放入 `responses`；第二阶段需要独立管理题目版本和共享权限，因此新增两个集合，而不是替换原有问卷结构。

### 4.2 问卷与答卷快照

`surveys` 中的 `versions` 数组保存草稿和发布版本。每个版本包含完整题目定义。发布版本不原地覆盖；修改已发布问卷时复制出新的草稿版本。

提交答卷时，`responses` 保存：

- `survey_id` 和 `survey_version`；
- `survey_snapshot.title` 和 `survey_snapshot.questions`；
- `answers`；
- 服务端计算的 `path`；
- `respondent_user_id` 和匿名显示标记；
- 提交时间和状态。

统计历史答卷时优先使用答卷自己的题目快照，而不是使用问卷当前草稿，避免后续编辑改变历史答卷的解释方式。

### 4.3 题目身份与题目版本

`question_items` 保存题目的稳定身份和管理信息，主要字段包括：

- `_id`、`owner_user_id`；
- `display_title`、`is_shared`；
- `current_version_id`、`latest_version_number`；
- `derived_from_item_id`、`derived_from_version_id`；
- `created_at`、`updated_at`。

`question_versions` 保存不可变内容，主要字段包括：

- `_id`、`question_item_id`、`version_number`；
- `content`；
- `created_by_user_id`、`created_at`；
- `based_on_version_id`；
- `restored_from_version_id`。

创建题目时生成 v1。修改内容时插入新版本，旧版本不覆盖。恢复历史版本时复制历史内容并创建新的最大版本号，而不是把当前版本指针直接改回旧记录。

### 4.4 题目复制与来源字段

从题库加入问卷时，服务端深复制指定版本的完整 `content`，生成问卷内唯一的 `qlib_...` 本地 `question_id`，并写入：

- `source_question_item_id`；
- `source_question_version_id`。

问卷保存的是题目快照，不是题库引用。因此题库以后创建新版本、恢复旧版本或取消共享，都不会反向修改已存在的问卷和历史答卷。

普通问卷创建接口不信任客户端提供的来源字段。普通 PATCH 更新题目时，只有题目内容与服务端现有快照完全未变，才保留服务端已有的合法来源标识；如果内容实际改变，来源标识会被清除。只有“从题库加入问卷”的内部可信路径可以写入新的来源关联。这项处理避免修改后的内容继续被错误统计为原题目版本。

### 4.5 索引

应用启动时创建的主要索引包括：

| 集合 | 索引与作用 |
| --- | --- |
| `users` | `username_normalized` 唯一索引，保证用户名唯一 |
| `surveys` | `share_slug` 唯一索引；`owner_user_id, updated_at` 用于问卷列表 |
| `responses` | 问卷和提交时间、问卷版本、填写者与问卷、重复提交、答案题目和来源题目版本索引 |
| `question_items` | 所有者更新时间索引、共享状态更新时间索引 |
| `question_versions` | `(question_item_id, version_number)` 唯一索引、题目创建时间索引 |

## 5. 核心算法与业务规则

### 5.1 答案校验

`validate_answer()` 对答案对象的题目 ID、题型和值进行校验，并区分答案缺失、显式空值和无效答案。

- 单选题：答案必须是题目中存在的 `option_id`。
- 多选题：答案必须是无重复的合法选项列表，并满足最少、最多或精确选择数量。
- 文本题：答案必须是字符串，并满足必答和长度限制。
- 数字题：拒绝布尔值、非数值、`NaN`、正负无穷，并检查整数、最小值和最大值。

测试保留了 `10**10000` 超大整数边界，用于验证算法不会因整数转换或比较异常而失效。

### 5.2 问卷定义校验

`validate_survey_definition()` 在发布前检查题目 ID、顺序、题型、选项、校验规则、跳转操作符、规则优先级、跳转目标和循环。第二阶段独立题目允许暂时包含跨题跳转目标，但加入问卷后仍由正常发布校验检查真实目标；缺失目标会返回 `invalid_jump_target`，不会静默删除规则。

### 5.3 跳转和提交路径

`resolve_next_step()` 按题目 `order` 和跳转规则 `priority` 计算下一步。第一条匹配规则生效，没有规则匹配时进入下一题，最后一道题结束。

`validate_submission()` 不信任客户端路径，而是从第一题开始重新遍历已发布问卷。它只要求实际路径上的必答题有答案，允许跳转合法跳过必答题，并拒绝未知题目答案、路径外答案、无效答案、运行时循环和非法目标。

### 5.4 题目版本统计

跨问卷统计只合并相同 `source_question_version_id` 的已提交答卷，并使用答卷自己的 `survey_snapshot.questions` 定位本地题目 ID。无答案、空字符串、空数组或校验失败的答案不计入有效样本。

- 单选题：各选项次数及占有效作答人数的比例。
- 多选题：各选项次数及比例，分母为有效作答人数。
- 数字题：有效样本数、平均值、最小值和最大值。
- 文本题：只返回有效文本数量，不返回原始文本内容。

统计接口限制为题目所有者访问，不返回填写者身份或其他问卷的原始答卷。

## 6. 权限与兼容性设计

所有题目库接口均要求登录。题目所有者可以创建版本、恢复版本和修改共享状态；其他用户只能读取已共享题目、把指定版本加入自己的问卷，或派生为自己的独立题目。派生后的题目拥有新的所有者和独立版本序列，修改不会影响原题。

取消共享只影响后续访问，不破坏已经复制到问卷或答卷中的快照。旧问卷和旧答卷没有来源字段时继续使用第一阶段逻辑，不自动猜测或迁移来源，也不会被错误纳入题目版本跨问卷统计。

问卷所有者只能访问自己的问卷和统计。分享问卷定义的 GET 接口可以公开读取；导航和提交需要登录。匿名填写仍是“登录后对所有者隐藏身份”，系统内部保留填写者 ID 用于重复提交控制。

## 7. API 与前端实现

### 7.1 API 分组

| 分组 | 主要接口 |
| --- | --- |
| 认证 | `POST /auth/register`、`POST /auth/login`、`GET /auth/me` |
| 问卷 | `POST/GET /surveys`、`GET/PATCH /surveys/{id}`、发布、关闭、统计 |
| 分享答题 | `GET /surveys/share/{slug}`、`POST .../next`、`POST .../submit` |
| 题目库 | `GET/POST /question-items`、题目详情、共享状态和版本历史 |
| 版本与派生 | 创建版本、查看版本、恢复版本、派生题目 |
| 复用与统计 | 加入问卷、使用情况、同版本跨问卷统计 |
| 健康检查 | `GET /health`、`GET /health/db` |

完整路径和请求说明沿用 `docs/api.md`，FastAPI 启动后也可以通过 `/docs` 查看 OpenAPI 页面。

### 7.2 前端

前端位于 `frontend/index.html`、`frontend/styles.css` 和 `frontend/app.js`，由 FastAPI 根路径直接提供，无需 Node.js 构建步骤。页面支持：

- 注册和登录；
- 创建、编辑、发布和关闭问卷；
- 显示问卷版本、截止时间和分享链接；
- 打开分享问卷、答题和提交；
- 查看问卷统计；
- 在“我的题目”和“共享题目”之间切换；
- 创建题目、查看详情和版本内容；
- 创建新版本、恢复历史版本、共享或取消共享；
- 派生共享题目；
- 选择问卷和指定题目版本加入草稿；
- 查看使用情况和跨问卷统计。

原有 JSON 编辑入口保留，用于高级题目配置和第一阶段工作流兼容。

### 8.2 最终完整测试

最终使用项目 `.venv` 中的 Python 3.10.7 和 pytest 9.1.1 执行：

```powershell
$env:PYTHONPATH = (Get-Location).Path
.\.venv\Scripts\python.exe -m pytest
```

实际结果：

```text
141 passed, 0 failed, 0 errors, 4 warnings in 7.48s
```

4 条 warning 均为依赖弃用提示：1 条是 FastAPI TestClient 使用旧 `httpx` 集成的提示，3 条是旧版 `HTTP_422_UNPROCESSABLE_ENTITY` 常量提示，不影响业务测试结果。本次没有为消除 warning 升级依赖或进行无关重构。

超大整数参数化用例的针对性验证结果为：

```text
20 passed
```

该修复没有删除、缩小或跳过 `10**10000` 测试，只为 pytest 参数化用例提供稳定的显式 ID，避免 pytest 9 在收集阶段为了生成显示名称而把超大整数转换成十进制字符串。

`git diff --check` 执行成功并返回退出码 0；但当前仓库文件均显示为未跟踪状态，因此不能据此声称所有项目文件都完成了 Git 差异检查。提交前仍需建立有效的 Git 跟踪和提交基线。

### 8.3 第二阶段自动化重点验证

第二阶段测试覆盖：

- 创建题目产生 v1，新增版本产生 v2，恢复旧版本产生新版本且历史内容不变；
- 未登录限制、共享读取、非所有者禁止修改和派生独立性；
- 指定版本完整复制、本地题目 ID 唯一和来源 ID 正确；
- 取消共享或题库更新后既有问卷快照不变；
- 缺失跳转目标时发布明确失败；
- 使用情况识别具体问卷版本和来源版本；
- 四种题型跨问卷统计和不同来源版本隔离；
- 普通创建或 PATCH 不能伪造题目来源；
- 修改题库副本内容后清除来源，不再参与原版本统计；
- 仅修改问卷标题时保留合法来源；
- 正常从题库加入后的来源和统计仍然有效。

## 9. 问题处理记录

### 9.1 来源标识可信边界

第二阶段验收中发现，普通问卷创建和 PATCH 曾允许客户端直接携带 `source_question_item_id` 和 `source_question_version_id`。由于使用情况和跨问卷统计依赖这些字段，伪造来源或修改内容后保留来源会污染统计。

修复后，普通创建清除来源字段；普通 PATCH 只从服务端旧快照恢复完全未修改题目的合法来源，修改内容则清除来源；题库加入接口使用内部可信参数保留服务端设置的来源。针对性测试证明伪造来源无效，合法题库复用仍可正常统计。

### 9.2 pytest 9 超大整数收集错误

完整测试最初在收集阶段失败。原因不是业务算法，而是 pytest 9 为参数化用例自动生成 ID 时尝试将 `10**10000` 转为字符串，触发 Python 4300 位整数转换限制。

修复方式是给原有数字边界参数化用例添加显式 ID。超大整数仍以原值执行，最终相关文件 `20 passed`，完整测试 `141 passed`。

### 9.3 其他已处理边界

第一阶段已处理乱序题目、重复顺序、无效选项、多选重复项、文本长度、数字有限性、路径外答案、未知答案、循环和最大步数等边界。发布后编辑创建新草稿，历史版本和答卷快照不直接覆盖。

## 10. 已知限制

- `start_question_id` 尚未实现，导航和提交从按 `order` 排序后的第一题开始。
- 只保存最终提交答卷，没有进行中答卷和断点续答。
- 没有独立的原始答卷明细和导出接口。
- 题目版本创建与 `question_items.current_version_id` 更新是两步写入；没有引入 MongoDB 事务。
- 题目使用情况当前扫描问卷版本，跨问卷统计当前扫描已提交答卷，适合课程项目规模，但未做大数据量性能验证。
- 前端功能已接通，但自动化前端测试仅检查入口和脚本可访问，没有完整浏览器 E2E 套件。
- 旧数据没有来源字段时不会自动迁移，也不会纳入题目版本统计。
